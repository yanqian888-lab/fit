一、产品概述
1.1 产品定位
本产品是一款虚拟宠物陪伴式减脂工具，以「用户与一只努力减脂的小熊猫并肩减脂」为核心叙事。产品用养成类游戏的情感化反馈替代传统减脂工具的冰冷数据记录，通过「用户减脂行为 = 宠物养成资源」的强绑定关系，降低减脂记录的心理门槛，提升用户的长期坚持动力。
小熊猫的人设是一个为减肥系统学习过营养搭配与健身运动学知识、精通减脂方法、平时热爱四处闲逛享受生活的伙伴。它既是用户的情感陪伴对象，也是具备专业能力的减脂顾问，与用户是「并肩减脂的搭子」关系，而非单向饲养的宠物。
1.2 目标用户
核心用户为有减脂、体重管理、健康饮食与规律运动诉求，但缺乏持续记录动力、容易在传统工具的枯燥记录中放弃的人群。这部分用户对情感陪伴、正向激励、轻量化记录有明确偏好，愿意为陪伴感与养成体验付出使用时长与一定付费。
1.3 核心价值与设计逻辑
产品围绕三条闭环构建体验：
激励闭环：
用户完成减脂记录或运动后获得浆果或鲜花，用于喂养宠物、购买器材，进而解锁食谱与多巴胺事件，获得正向情感反馈并持续坚持。
记录闭环：
聊天自动记录与手动记录双入口互补，前者低门槛、后者精准化，共同保证数据完整。
情感闭环：
日常聊天陪伴、亲密互动提升心情、宠物外出带回治愈内容，逐步强化用户的情感依赖，提升留存与使用频次。

三、Tab1 聊天 AI 助手
聊天 Tab 是 App 默认首页与核心交互入口，承载日常陪伴、减脂答疑与轻量化自动记录。为兼顾「即时响应、专业深度、记录准确」三重目标，聊天能力由三个各司其职的Agent协作完成，对用户表现为一只统一人设的小熊猫，底层由路由分发到不同Agent处理。
3.1 三Agent协作架构
用户每一条消息先进入意图路由层，由其判断消息类型并分发给对应Agent；多个Agent可就同一条消息接力处理（例如先由沉淀Agent抽取记录、再由管家Agent汇总反馈）。三个Agent的定位与边界如下：
3.1.1 管家Agent（即时任务处理与信息汇总）
管家Agent是用户诉求的第一响应者，负责把用户的口语化诉求转化为具体动作并即时反馈。它处理的即时任务包括：接收记录类意图后触发记录确认弹层、执行签到/喝水/打卡等一键动作、响应「今天吃了多少卡」「这周瘦了多少」等查询、按用户指令设置或调整提醒、引导跳转到轻断食/陪你动/商城等功能页。
信息汇总方面，管家Agent负责将分散的记录聚合为可读的简报，例如当日摄入与消耗热量对比、三大营养素结构、体重变化趋势、任务完成进度与货币结余，并在恰当时机（如晚间）主动推送当日总结。记录或任务完成后，由它统一发放浆果/鲜花奖励并回执，奖励数值取自后端配置。
3.1.2 专家Agent（专业知识输出）
专家Agent承接所有需要专业判断的问题，如「减脂期能不能吃这个」「这套动作练哪里」「我这个体重该怎么安排饮食」。它结合用户的身高、体重、体脂、减脂目标等基础数据，输出个性化、可执行的营养与运动建议，并可推荐对应食谱或训练方案，推荐结果可一键沉淀到食谱库或同步到陪你动。
专家Agent的知识边界、话术风格与安全红线（如不提供极端节食、医疗诊断类建议）由后端话术库与规则配置约束，保证输出既专业又符合合规要求。
3.1.3 沉淀Agent（内容分辨与沉淀）
沉淀Agent负责在自然对话中「听懂并记下」有价值的信息。它先做内容分辨——判断一句话是纯闲聊、情绪表达，还是包含可结构化的减脂数据；再对可记录内容做抽取与归一，例如把「中午吃了碗牛肉面」解析为餐次、食物、预估份量与热量，把「今天有点丧」识别为心情感悟。
抽取结果分两种去向：数据类（饮食/运动/体重围度/饮水）交给管家Agent触发记录确认弹层，经用户确认后落库；内容类（心情感悟、搭子给出的食谱）在识别后沉淀到心情日记、食谱库。识别的关键词规则、置信度阈值与分类规则均由后端可配置。
3.2 意图路由与接力流程
用户每一条消息先进入意图路由层，按以下分类判定后分发到对应Agent。单条消息可触发多个Agent接力处理。路由规则可配置：关键词权重、置信度阈值、分类优先级、接力顺序均在「AI与Agent配置」模块中调整。
三Agent接力处理流程示例——以「中午吃了碗牛肉面，减脂期能这么吃吗」为例：
1. 意图路由层识别为「记录类-饮食 + 知识答疑类」混合意图
2. 沉淀Agent抽取结构化数据：餐次=午餐、食物=牛肉面、预估份量=1碗、预估热量=约550kcal
3. 管家Agent弹出饮食记录确认弹层，等待用户确认/修改/取消
4. 专家Agent并行生成专业回复：牛肉面的热量构成、减脂期建议（替换为荞麦面/少喝汤/加蔬菜）
5. 用户确认记录后，管家Agent写入记录库、发放浆果奖励、回执一句话
6. 如专家给出了替代食谱，用户可点击「存进食谱库」由沉淀Agent写入搭子食谱

3.5 页面功能明细
四、Tab2 陪伴（宠物搭搭）
陪伴 Tab 是宠物养成主场景，承载宠物状态展示、喂食、运动、亲密互动、外出探索与货币消耗。多巴胺事件的触发、查看与收集均在本 Tab 完成，不跳转博物馆。
4.1 宠物状态机
宠物状态是养成系统的核心数据，由心情值、饱食度两个核心属性驱动，叠加居家/外出的位置状态。
4.2 居家互动三条引导逻辑
吃饭引导：
饱食度低于阈值时宠物头顶显示「吃饭叹号」气泡 → 用户点击 → 弹出背包食物选择 → 背包为空则跳转商城食物 Tab → 选择食物喂食 → 播放喂食动画 + 弹出反馈文案（从话术库随机）+ 饱食度/心情值上升。
运动引导：
到预设运动时间或用户主动点击运动 → 判断是否需要器械 → 需要则从背包取/跳转商城购买 → 准备就绪后判断App内是否有对应运动跟练 → 无跟练：背景播放宠物运动动画，计时结束后发放奖励；有跟练：弹窗让用户选「跟练」或「只让搭搭动」→ 跟练跳转陪你动页，不跟练则背景动画。
心情引导：
心情值低于阈值时显示低落状态+叹号气泡 → 用户点击 → 三个选项：摸一摸（当前页播动画+5心情）、抱一抱（当前页播动画+10心情）、聊会天（跳转聊天 Tab）。每日互动有上限，达到后只播动画不加数值。

5.5 生成今日分析
用户点击按钮 → 判断是否满足生成条件（至少有饮食或体重记录）→ 弹出消耗确认弹窗（显示消耗货币类型与数量，文案从配置读）→ 确认后扣除货币 → 工具服务生成分析报告 → 展示在当前页+自动存入博物馆每日分析历史。
今日分析报告结构：
1. 总览一句话：今天热量缺口/盈余多少，整体表现评价
2. 饮食分析：总热量、三大营养素占比是否合理、偏高/偏低项建议
3. 运动分析：总消耗、运动类型分布、是否达标
4. 体重趋势：近7天/30天趋势、波动解读
5. 饮水与断食：达标情况
6. 搭子寄语：小熊猫口吻的鼓励或建议（从话术库抽取）
7. 明日小目标：基于今日数据给出1条可执行建议
报告模板、各模块口径、生成条件均由后台「减脂工具配置」模块配置。生成今日分析所消耗的货币类型（浆果/鲜花）与具体数值均由后台配置，不在前端写死。
5.6 陪你动
运动跟练流程：
1. 用户选择运动项目（跳绳/深蹲/平板支撑/走路等）
2. 判断是否需要器械 → 需要则检查背包是否拥有 → 无则跳转商城购买
3. 设置目标（时长/个数），默认值从配置读取
4. 开始跟练：循环播放标准动作动画+实时计时/计数语音+小熊猫陪练画面
5. 结束：显示本次数据（时长、个数、估算消耗）→ 自动写入运动记录 → 发放浆果奖励
6. 可选：看广告得额外浆果（预留位，当前版本关闭）

六、Tab4 博物馆
博物馆是用户成长沉淀与收集中心，集中展示减重进度、成就、心情日记、食谱与每日分析记录。博物馆主页各入口在后台均支持配置开关，控制是否开放。
6.1 数据总览
同时陈列减重、连续打卡、食谱收集类成就，达成自动发放鲜花奖励。可配置项：成就达成条件、鲜花奖励数量、徽章素材。
6.2 食谱库
食谱库分三类 Tab：系统食谱（官方预置）、搭子食谱（AI推荐后用户保存的）、自定义食谱（用户手动添加的）。
6.3 里程碑
里程碑是减重维度的长期成就，按体重下降量分级。每达成一个里程碑弹出成就卡片+鲜花奖励+对话内通知。里程碑节点数值、奖励、卡片样式均可配置。
6.4 心情日记
沉淀Agent自动抽取的心情表达+用户手动记录的感悟，按时间倒序排列。每条包含：日期、心情标签（开心/平静/低落/焦虑/斗志满满）、正文、关联的当日体重或事件（可选）。支持手动新增、编辑、删除。可配置项：情绪分析维度、日记标签体系。
6.5 每日分析历史
按日期归档所有生成过的今日分析报告，可回看、可分享。列表展示日期+一句话摘要，点击进入详情。生成次数、是否付费解锁、报告版本号均有记录。博物馆主页各入口开关（是否开放）由后台配置。

7.3 V2.1关键决策
以下为本版本关键决策结论，对应同步影响前文相关模块。
7.3.1 三Agent分工对前端不可感知
聊天 Tab 的管家Agent、专家Agent、沉淀Agent三者分工仅存在于后端架构层，对用户完全不可感知。前端始终呈现为一只统一人设的小熊猫，回复口吻、语气、形象保持一致，不通过不同样式、不同身份标识、不同头像等方式区分Agent。路由与接力全部在后台完成，用户无感知。
7.3.2 生成今日分析消耗可配置
生成今日分析所消耗的货币类型（浆果/鲜花）与具体数值均由后台配置，不在前端写死。运营可根据经济体系平衡与用户反馈动态调整。
7.3.3 宠物成长长线当前版本暂不做
当前版本不纳入宠物成长长线体系（如体型变化、等级体系、生活方式维度、三维属性成长等长线养成玩法）。宠物状态仅保留心情值、饱食度等短期属性与居家/外出状态切换，成长长线留待后续版本根据数据再评估。
7.3.4 付费与会员体系当前不做，预留广告接入位
当前版本App完全免费，付费与会员体系不纳入首发。但为后续接入广告变现做准备，在以下场景预留广告观看操作位——当前版本用户无感知、不实际展示广告，仅在产品结构与埋点上预留接入位置，待广告SDK接入后可直接开启：
以上广告位当前版本全部默认关闭、用户无感知，仅在后端配置体系中保留对应开关与文案配置位，广告SDK与审核合规工作完成后再行开启。

• 前台静默：App前台运行时，通知栏推送自动降级为对话内消息，不打扰当前操作。

十一、后端技术架构与迭代规划
本章从技术架构视角定义后端服务的分层设计，与第十章「后端配置体系（CMS）」形成互补——第十章定义配置什么（12个配置模块），本章定义谁来承载（服务拆分与数据分层），两者通过统一配置中心串联。
11.1 三层架构总览
后端整体分为接入层、业务服务层、数据存储层三层，业务服务层内包含统一配置中心，所有业务服务的可配置项均从配置中心读取，不各自维护配置逻辑。
11.2 接入层
App端接口：
面向App前台的统一API网关，负责鉴权、限流、路由分发到各业务服务。
CMS管理后台：
运营与产品的可视化配置入口，对应第十章12个配置模块的操作界面，写入统一配置中心。
推送服务：
统一管理对话内消息、应用内弹窗、通知栏推送的下发，触发条件与文案由消息与推送配置模块驱动。
第三方接入：
广告SDK、第三方登录、支付通道、AI大模型接口等外部能力的接入与封装。
11.3 业务服务层（8个服务+统一配置中心）
8个业务服务按领域拆分，各自独立部署、通过接口互相调用。所有服务的可配置参数均不硬编码，统一从配置中心读取，运营在CMS修改后实时或准实时生效。
11.3.1 统一配置中心
统一配置中心是业务服务层的横向基础设施，承接CMS管理后台写入的全部12类配置，以key-value或结构化配置的形式存储到配置数据库，并推送给各业务服务。核心能力包括：配置版本管理（支持回滚）、灰度发布（按用户分组下发不同配置）、实时生效（热更新，无需重启服务）、变更审计日志（谁改了什么、什么时候改的）。
设计原则：凡数值、文案、开关、规则、概率、上限、奖励等运营可能调整的项，一律走配置中心，不写死在代码里，与第十章「全量可配置」的产品原则对齐。
